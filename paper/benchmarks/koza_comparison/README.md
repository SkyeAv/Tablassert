# Koza comparison: mapping and resolution workloads

The same deterministic 10,000-row CSV (`tutorial-data-10k.csv`, generated by
`make_10k.py`) supports three explicitly separate workloads:

1. `tablassert_*`: `tutorial-graph.yaml` and `tutorial-table.yaml` build the graph
   with local fullmap resolution, category prioritization, deduplicated KGX NDJSON
   nodes, provenance, and a RIG.
2. `koza_mapping_only_*`: `tutorial-koza.yaml` and `tutorial-transform.py` map each
   row to KGX TSV but emit raw labels as node IDs. This isolates mapping cost; it is
   not a resolved-graph comparison.
3. `koza_hosted_resolved_*`: `tutorial-koza-resolved.yaml` and
   `tutorial-transform-resolved.py` deduplicate labels, call hosted NameResolution
   (four concurrent lookups, at most five candidates, `only_taxa=NCBITaxon:9606`),
   then call NodeNormalization in batches of 100 CURIEs. The top-ranked candidate
   supplies the canonical ID, preferred name, and categories. Empty or incomplete
   results fail the run. The HTTP implementation is imported from the sibling
   `name_resolution/bench_name_res.py` harness so both benchmarks use the same API
   workflow.

Koza 2.7.0 provides mapping tables but no built-in label resolver. Its
`@koza.transform()` whole-dataset hook supports this custom integration. Hosted
resolution therefore demonstrates additional code and network cost, not a missing
capability that cannot be implemented.

## Measuring

Run on the build host with both installed CLIs:

```bash
python make_10k.py
python measure_koza.py --repeats 3 \
    --tablassert /users/sgoetz/Code/dakp/.venv/bin/tablassert \
    --koza ./koza-venv/bin/koza --out timing.json
```

Every measurement includes a fresh CLI process. The first repeat of each workload
is labeled cold; immediate repeats are labeled warm. Output directories are removed
before every run. OS, database, and remote-service caches are never cleared, so
"cold" does not mean cold OS or service caches. Cold is one first-pass measurement; warm is three subsequent passes. They are
reported separately and are not pooled.

Each run verifies edge and node counts. Hosted runs also record unique terms,
complete canonical records, request counts, and resolution time in
`koza-hosted-resolution.json`, copied into the corresponding `timing.json` run.
Versions, platform, CPU count, and RAM are recorded.

## Output and policy differences

The workloads all perform tabular mapping, but their graphs are not equivalent:

- Tablassert emits 12,500 edges from 10,000 input rows because `pancreatic cancer`
  retains two equally ranked canonical CURIEs in the installed fullmap. It emits
  nine deduplicated nodes.
- Resolved Koza emits only the top hosted candidate, hence 10,000 edges. Its TSV
  writer emits two node records per input row (20,000 node rows), including repeats.
- Mapping-only Koza also emits 10,000 edges and 20,000 repeated node rows, but IDs
  are unresolved input labels.

Consequently the timings compare implementation and infrastructure costs for these
workloads, not throughput of identical graphs. Hosted candidate ranking, taxon
handling, and tie behavior differ from local fullmap ranking. A small synthetic
input with eight unique labels measures per-workflow overhead; it does not
represent resolution throughput on a large vocabulary.

## Configuration trade-offs

Tablassert's basic table recipe has 29 counted lines and its separate graph wrapper
24; Koza's mapping-only YAML and Python transform have 25 and 31. Blank lines,
comments, and Python docstrings are excluded by `count_loc.py`. The resolved Koza
configuration and integration module have 25 and 86 counted lines, excluding the
shared HTTP client imported from the name-resolution benchmark. These counts
illustrate where logic lives; they are not a general complexity metric.

Tablassert's advantage here is integrated, offline, batched resolution with
column-aware policy and graph-level outputs. Its costs are the 92.9 GB fullmap and
building or obtaining that versioned resource. The hosted Koza arm avoids that
local store and can use current service content, but needs imperative integration
code and inherits network latency, availability, rate limits, and remote-version
drift. Mapping-only Koza is cheaper because it does less work, not because it is a
faster equivalent resolver.
